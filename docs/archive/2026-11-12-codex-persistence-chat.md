已经验证的部分：

- **数据库基础闭环通过**：十万字符分块写入、范围读取、条件版本更新、事务回滚、关闭重开和应用重启恢复。还没验证主应用与扩展的真实多进程竞争。
- **原生跨片段编辑基本可行**：RichEditor 的跨片段选区、全选、复制、粘贴和删除通过合成文字测试；普通控制器模式也有当前设备的中文输入手验记录。
- **全量加载的性能问题已经明确**：十万字密集多段场景，逐片段导入至空闲帧约 1.3 秒、总 PSS 约 276 MiB；两个批量方案约 836～932 MiB，其中发生过内存阈值杀进程，因此目前不采用。以上不是正式冷打开或峰值内存指标。

现有长文原型虽有懒创建节点，但数据仍一次性生成在内存中；缺少数据库按需读取、块内精确定位和高度补偿，单块 TextArea 也解决不了跨块选择。

**下一步建议完成一个独立的“长文打开、定位、进入编辑”实验闭环：**

1. 从试验数据库按范围读取，浏览态只渲染目标附近内容。
2. 支持恢复到块内具体位置，验证高度修正、图片加载和滚动时可见内容是否跳动。
3. 在同一原型中验证点击进入 RichEditor 的时机、光标衔接和内存成本，重点检查是否又退回全量加载。
4. 对两万／十万字、无换行／密集多段场景重复采样，确定可接受的性能阈值。

这个闭环验证通过后，再补真实图片、长文剪贴板、复杂字符与手指选区，以及真实多进程竞争，最后确定表结构和位置契约，进入正式迁移。

我的判断是：**需要验证新的编辑架构，RichEditor 只保留为候选控件。现在没有证据证明，配合其他优化就能解决它的十万字性能问题。** 我上一条把“进入 RichEditor”写成既定下一步，表达得过于确定。

已有结果足以否定当前几种全量加载实现直接进入正式方案，但还不足以否定 RichEditor 的所有用法。这里要区分两个问题：

- **浏览态按需渲染**可以减少打开笔记时的加载和排版成本。
- **进入编辑后仍把全文装进 RichEditor**，原来的延迟和内存瓶颈仍可能出现。这只是推迟问题，不能算解决。

因此，下一轮真正要验证的是：**能否让原生编辑器只承担有限范围的内容，同时保住完整的编辑体验。** 难点在跨范围选区、全选、连续删除、长文粘贴、中文预输入和撤销。此前多个独立 TextArea 的方案已经暴露跨块选区限制，不能直接作为替代。

我建议把下一步调整为一次有明确退出条件的选型实验：

1. 验证“局部加载的 RichEditor”能否同时满足核心编辑行为和性能要求。
2. 如果必须加载全文才能保住这些行为，且全文性能仍不达标，就停止这条路线，评估其他编辑引擎，例如 Web 编辑器；它也需要在鸿蒙设备上验证输入法、图片和内存，不能预设更好。

**我们要保留的是十万字笔记的产品要求，而不是 RichEditor 这个选型。** 在这个瓶颈解决前，不推进正式数据库迁移，也不把浏览态优化当作编辑方案已经成立。

用时 23秒

**有很强的借鉴价值，环境差异主要影响“能否直接用某个引擎”，不影响核心架构的借鉴。** 查阅官方资料后，我也要修正前面的建议：现阶段应优先比较成熟编辑引擎，而不是先假设我们能在 RichEditor 外面补出一套可靠的长文机制。

成熟编辑器通常把三件事分开：**文档如何保存在内存中、哪些内容需要排版显示、输入与选区如何作用于全文。** 数据库存储分块只解决其中一部分。

| 实例            | 主要做法                                                     | 对我们的启发                                         |
| --------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| VS Code         | 用 piece tree 管理文本，编辑时修改片段结构，避免频繁复制全文 | 改善输入、撤销与范围读取；但不能单独解决控件排版成本 |
| CodeMirror 6    | 保留完整文档模型，只为可见区域及缓冲区域创建显示节点；离屏高度先估算、显示时实测 | 编辑状态可以覆盖全文，而显示节点只覆盖局部           |
| Apple TextKit 2 | 文本引擎内部按视口进行非连续排版，直接处理目标区域           | 原生控件能否高效处理长文，取决于底层排版机制         |
| Scintilla       | 按行缓存排版结果，提供不同缓存范围，合并修改后再换行排版     | 性能需要在重复排版成本与缓存内存之间取舍             |

以上分别来自 [VS Code 实现说明](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation)、[CodeMirror 系统指南](https://codemirror.net/docs/guide/)、[TextKit 2 官方介绍](https://developer.apple.com/videos/play/wwdc2021/10061/)、[Scintilla 文档](https://www.scintilla.org/ScintillaDoc.html)。

**最关键的区别是：成熟方案把“显示不完整”与“文档、选区不完整”分开了。**

例如，CodeMirror 虽然只渲染窗口附近的内容，但编辑器仍有全文模型、文档位置和选区。这与我们把正文拆成多个独立 TextArea 有本质区别：后者每个输入框只知道自己的文字，跨框选择和输入需要我们重新实现。[CodeMirror 系统指南](https://codemirror.net/docs/guide/)

因此，对我们有三个直接结论：

**第一，十万字不一定需要连内存中的文字也按需加载。**
按 UTF-16 文本单元粗算，十万个单元的原始字符数据约 200 KB，不含对象、样式、图片和排版开销。我们的实验出现数百 MiB 占用，说明应重点排查排版、样式对象、副本和控件生命周期；目前还不能确定具体归因。可以先保留完整的轻量文档模型，把按需处理重点放在昂贵的排版与显示上。

**第二，外层 LazyForEach 不能自动赋予 RichEditor 内部虚拟排版能力。**
如果一个 RichEditor 仍持有全文，外层列表不会自然消除它内部的全文成本；如果改成多个局部 RichEditor，又要解决全局选区、输入法和撤销。这是架构成本，不能当成普通性能优化。

**第三，Web 编辑器值得现在就做对照，但要选对类型。**
CodeMirror 的视口机制与我们的长文瓶颈直接相关，适合作为文字长文的对照基线；图文笔记则还需要验证图片、段落和交互适配。ProseMirror 提供结构化文档、事务和共享未修改节点的机制，但不能仅凭这些就推断它已解决我们需要的长文虚拟排版问题。[ProseMirror 官方指南](https://prosemirror.net/docs/guide/)

我的建议是把下一步改为**编辑引擎选型实验**：

1. 在鸿蒙 Web 组件里验证 CodeMirror 6，用同一批十万字数据测打开、连续输入、中文预输入、手指跨屏选区、长文粘贴和内存。
2. 核对当前 API19 的 RichEditor 是否提供可用的内部按需排版能力，并对现有高内存结果做定向归因；给这条调查设定有限范围。
3. 对照结果后决定：继续原生、采用 Web 引擎，或进一步比较图文编辑框架。

**我目前更倾向于先验证成熟引擎在鸿蒙上的适配成本。** 自己围绕局部 RichEditor 重建跨全文编辑机制，实际上已经接近开发编辑器内核，现阶段不应把它作为默认路线。
