# Windows 工作区文件无法编辑

整理日期：2026-11-12。来源为本项目实际排查，供其他 Agent 复用排查方法；不是通用的一键修复脚本。

## 症状与本次原因

文件位于声明的可写工作区，却出现部分可写、部分不可写，报 `EPERM`、`Access Denied`、Git `unable to unlink` 或构建日志写入失败。仅凭这些错误不能直接认定原因。

本项目原来以 `note_demo` 为工作区，后来从上一级 `gpt-root` 工作。排查发现：一些文件仍有旧工作区沙箱身份的 ACL 授权，但缺少当前工作区能力 SID 的授权。当前受限进程令牌无法通过访问检查。这是已证实的直接原因；不能据此断言所有工作区切换都会导致该问题，也未确定是哪次操作造成 ACL 同步不完整。

## 排查顺序

1. 核对当前任务的可写根、实际路径和链接目标，排除越界、只读属性及链接重定向。
2. 对比一个可写文件与一个失败文件的 ACL，连同父目录检查继承和显式拒绝项。
3. 确认执行进程身份及**受限令牌 SID**。`whoami` 或文件所有者不能单独证明沙箱有效写权限；本次读取 Windows `GetTokenInformation(TokenRestrictedSids)`，对照实际能力 SID。
4. 申请写入/删除访问句柄验证权限，使用 `OPEN_EXISTING`，不截断、不写字节、不设置删除关闭标志，随后立即关闭。不要通过改写真实源码试权限。
5. 对照失败项是否缺少当前沙箱身份的授权。若返回共享冲突等其他错误，应另查文件占用；不要套用本次结论。

基础只读检查示例，路径替换为实际受检文件：

```powershell
$filePath = 'D:\WorkSpaces\gpt-root\note_demo\docs\pages.md'
Get-Item -LiteralPath $filePath -Force | Select-Object FullName, Attributes, LinkType, Target
Get-Acl -LiteralPath $filePath | Format-List Owner, AreAccessRulesProtected, Sddl
whoami /user
whoami /groups
```

本次还参考本机 Codex 的 `cap_sid` 映射，并与运行进程受限 SID 交叉验证。该文件属于实现细节，不保证所有版本都有；不能只根据配置映射猜测当前身份，更不能复制别的机器或会话的 SID。

## 本次修复方法

- 先备份受检项目文件、目录的原始 ACL，记录目标范围和待修清单。
- 获得用户授权后，只对项目内缺失项补充**当前已授权工作区沙箱身份**的 `Modify` 权限；目录按需允许文件和子目录继承。保留原授权与所有者。
- 普通沙箱外进程仍被 Windows 拒绝修改 ACL，最终通过管理员 UAC 执行同一份限定范围的修复方案。**沙箱外运行不等于 Windows 管理员运行。**
- 未修改文件内容，未关闭沙箱，未给 `Everyone` 开放写权限；`.git`、Agent 配置、安全目录及依赖目录不在显式修复范围。

不要把“允许编辑项目”扩展为任意修改系统权限。其他环境应先定位原因，再审批具体修复方案；优先考虑正确初始化工作区权限，避免长期堆叠不明 SID。

## 修复验收

必须回到普通沙箱验证，不能只看管理员命令成功：

- 原先失败文件能取得写入和删除访问句柄。
- 在目标目录对专用临时文件进行新建、写入、重命名、删除；操作前确认目标范围，不碰业务文件。
- 原先失败的 Git 或构建操作恢复；确认没有意外内容差异。

本次87个代码、文档和配置文件中，原30个失败项全部恢复；扩大检查发现的144个缺失项经显式授权和继承补齐。文档、脚本、页面目录临时文件操作通过，普通沙箱增量构建通过，源码内容未变。

**审批规则与文件 ACL 是两层机制。** 命令自动批准不代表 Windows 一定允许访问；子 Agent 继承会话策略，也不会自动修复文件 ACL。

本机详细备份和探针结果在忽略目录 `note_by_agent/build/verification/permissions/`，不保证新检出或其他机器存在。排查方法以本文为入口，不依赖这些临时产物。
